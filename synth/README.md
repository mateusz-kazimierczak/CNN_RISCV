# NTHU ASIC synthesis

Use `python3 tools/nthu_synth.py` from the repository root (local Python **3.9+**,
standard library only). Jobs execute on NTHU EE Linux through Daisy; synthesis
never runs on the Mac. Start with the registered-adder smoke design. The real
B0/B1 manifest is generated by `tools/cvw/prepare_synth.py`. X1 and later
extension RTL now exists and has passed full-model simulation, but extension
synthesis still needs inspected configuration-specific manifests. The original
example templates retain their placeholders. Actual mapping is blocked by the
[recorded DC startup failure](../results/synthesis/baseline/README.md).

## Quick start

```sh
# Offline: prints every payload path/hash and remote staging command. No SSH/writes.
python3 tools/nthu_synth.py submit --config synth/configs/smoke.json --dry-run
python3 -m unittest discover -s synth/tests -v

# Site settings are user-owned and ignored by Git. Never add passwords/tokens.
cp synth/configs/nthu.example.json synth/configs/nthu.local.json
python3 tools/nthu_synth.py doctor
```

The example routes `u115123101` through `daisy.ee.nthu.edu.tw:11922` to `ws25:22`.
Only Daisy needs laptop DNS resolution. Both hops use system OpenSSH, batch
mode and strict host-key checking. Establish trusted host keys and supported,
authorized agent/key access manually first. Password-interactive login is fine
for manual diagnostics; the automation never collects passwords. An optional
snippet for **you to merge**, without replacing `~/.ssh/config`:

```sshconfig
Host nthu-ee-daisy
    HostName daisy.ee.nthu.edu.tw
    User u115123101
    Port 11922

Host nthu-ee-ws25
    HostName ws25
    User u115123101
    ProxyJump nthu-ee-daisy
```

Check `ssh nthu-ee-ws25 'hostname; echo $HOME'`. The CLI supplies its own equivalent
connection options, including batch/host verification on the proxy child, so it
does not need these aliases. Existing OpenSSH identity/agent configuration still
applies. Keep host verification enabled. Legacy algorithms are never enabled by
the CLI; any necessary compatibility exception must be explicit and host-scoped
(see the ws25 instructions below). Once authorized, `ssh-add` can make an already configured key available.
The CLI's `--site PATH` option precedes the subcommand.

`doctor` reports local transfer tools, end-to-end connectivity, host/home/shell,
noninteractive shell execution, disk space, prospective work-directory access,
remote transfer tools and scheduler discovery, library readability, and DC release
selection in the same `tcsh -f` environment used by jobs. It does not submit a
process, create the work root, or check out a compile license by default.

Before submitting anything, obtain course/site confirmation of:

1. Permitted use of the candidate **demo** SAED32 library and the chosen corner.
2. The approved execution mechanism. Select `execution: "sge"` for approved
   `qsub`, `"slurm"` for approved `sbatch`, or `"nohup"` **only if departmental
   policy permits detached jobs**. Scheduler presence alone proves no permission.
3. Set `library_use_confirmed` and `execution_policy_confirmed` to `true` in the
   local site file. Keep the compile choice explicit (`compile` or `compile_ultra`).

The tool is pinned to `2020.09-sp5`, sourced from
`/usr/cadtool/user_setup/08-synthesis.csh`; the worker checks the actual DC banner
before running. This release's `dc_shell -version` prints its banner but exits 1;
the preflight and worker validate the banner rather than treating that help-mode
exit as a failed compilation. The known default 2025.06 fails on this host. No shared installs,
symlinks, libraries or license configuration are changed. Qualifying another DC
release requires updating the version guards and tests as well as configuration.

```sh
# After the above policy checks: submits ONE tiny sequential design.
python3 tools/nthu_synth.py doctor --smoke
# Equivalent explicit submission after successful doctor:
python3 tools/nthu_synth.py submit --config synth/configs/smoke.json

# Substitute the printed ID. Stop following logs with Ctrl-C; the job continues.
python3 tools/nthu_synth.py status <job-id>
python3 tools/nthu_synth.py logs <job-id>
python3 tools/nthu_synth.py logs <job-id> --follow
python3 tools/nthu_synth.py fetch <job-id>
```

Inspect the fetched `logs/version.log`, `reports/library.rpt` (units and operating
conditions), `SYNTH_LIBRARY_CELLS` in `logs/dc.log`, `reports/check_design.rpt`,
`reports/check_timing.rpt`, mapped netlist, area and timing. Successful smoke
compilation validates the configured compile entitlement only; there is no silent
fallback from `compile_ultra` to `compile`. Library existence/readability alone
proves neither permission nor successful DC loading. The CLI references the `.db`
on the server; it never includes it in an upload or fetch.

## Packaging and flow

Design JSON supplies ordered `sources`, explicitly enumerated `headers`,
`include_dirs`, `defines`, `parameters`, real `top`, hardware `scope`, clock/reset,
I/O delays, extra SDC/Tcl `constraints`, and `allowed_blackboxes`. Paths are relative
to this repository. Relative include paths are preserved under `inputs/`;
**include directories are not recursively copied**. List every needed header,
include, initialization file or generated dependency explicitly. Supported input
extensions are `.sv`, `.v`, `.svh`, `.vh`, `.h`, `.sdc`, `.tcl`, `.json`; supporting
other generated memory formats needs an intentional allowlist extension. Symlinks
must resolve inside this repository. Files over 32 MiB and payloads over 256 MiB
are rejected. No checkout, model weights, testbench, executable or vendor DB is
uploaded automatically. Tcl/SDC inputs are trusted project code and execute as
such; JSON parameter/define/path values are quoted as data.

The remote toolchain needs POSIX `sh`, `/usr/bin/tcsh`, `tar`, `sha256sum`, `awk`,
`grep`, `readlink` and Linux `/proc`; no remote Python or recent Bash is used.
Transfer prefers mutually available rsync in jump mode. Otherwise gzip tar streams
through SSH (also in nested mode); `transfer: "tar"` forces this fallback. No scp
protocol compatibility is required. For separate manual scp commands, newer macOS
scp may need `-O` for a server lacking SFTP; establish that failure before using it.

`run_dc.tcl` uses one explicit target/link library, `analyze`/`elaborate`/`link`,
strict `check_design`, blackbox checks, a single clock, uncertainty and I/O delays,
then the configured compile command. Missing/inconsistent timing constraints,
unmapped cells, unresolved references and DC errors fail the job. The current
flow requires library time units of 1 ns and reports the library area units.
Reset is timed as an ordinary input unless a supplied constraint file explicitly
sets another policy. No reset false path is invented. Only one clock is supported.
Intentional blackbox references must be named explicitly; strict link/check_design
can still reject an incomplete macro model. Provide valid declarations/models
rather than suppressing errors. Blackbox logic area is excluded and must be
reported as such. These checks are intentionally conservative.

Every run produces checks, library metadata, area, cell references, ten max-delay
timing paths, QoR, machine-readable metrics/cell breakdown, mapped Verilog and SDC.
An output sentinel alone is insufficient: the worker also requires artifacts,
numerical metrics, successful input hash verification and no DC `Error:` messages.
Fetch cross-checks report area/slack against metrics and cell counts. Tcl command
or version incompatibilities fail explicitly and require qualification on the real
2020.09-SP5 installation; offline mocks cannot validate commercial tool APIs.

## Jobs, recovery, and comparison

Remote paths are under `$HOME/<remote_root>/<UTC-time>-<random-id>/` with private
permissions and `inputs/`, `scripts/`, `logs/`, `reports/`, `outputs/`, `status/`.
An upload first lands in a separate `.upload` directory and is renamed only after
transfer. Partial uploads never become jobs. A launch claim prevents duplicate
launches of one ID. The CLI returns after a verified worker start/completion or
scheduler acceptance; a queued scheduler job remains `STAGED`, with a scheduler ID.

Worker state follows `STAGED → RUNNING → SUCCEEDED|FAILED`, with atomic state
writes, exit code, hostname, PID/start identity, run path and UTC timestamps.
`status` checks PID **plus Linux process start ticks and working directory** for
RUNNING jobs, reporting `INTERRUPTED` liveness when the worker disappeared. It
never infers success from a missing process, a PID alone, or DC exit zero. There
is no automatic cancellation or process killing. A per-user `$HOME/<remote_root>/.active`
lock allows one synthesis at a time across this workflow, including scheduler
jobs. Jobs denied by an existing lock fail explicitly with code 75.

After network failure, use the printed ID with `status`, `logs`, and `fetch` before
retrying. A failed/ambiguous upload/launch is recorded locally in
`submission_error.txt`; it is never reported as running or successful. Make a new
submission with a new ID if staging never completed. Retain partial directories
for diagnosis; the tool does not delete remote runs. After a hard kill, a stale
`.active` lock deliberately remains: inspect its `owner`, job hostname and process
identity (and scheduler state if applicable) before manually removing **only that
stale lock**. A network interruption does not terminate a detached worker. Local
submission records must be retained to locate the original server for later fetch.

Fetched artifacts go to ignored `synth/results/<job-id>/`. Fetch is read-only on
the server and may run while synthesis runs; summaries are produced as measurements
only for completed, validated jobs. Manifests store exact file SHA-256 hashes,
configuration, Git commit/dirty flags (including source checkouts), tool settings,
source and script snapshots, submission command and server routing. Runtime status
and version logs complete the record. Do not put secrets in JSON or command lines.

```sh
# Only after replacing the blocked templates with inspected, verified RTL manifests:
python3 tools/nthu_synth.py submit --config synth/configs/cv_wally_b0.local.json --dry-run
# This flag is explicit authorization for ONE full core run; a matching smoke is mandatory.
python3 tools/nthu_synth.py submit --config synth/configs/cv_wally_b0.local.json \
  --allow-full-core --smoke-job <fetched-successful-smoke-id>
python3 tools/nthu_synth.py submit --config synth/configs/cv_wally_x1.local.json \
  --allow-full-core --smoke-job <fetched-successful-smoke-id>
python3 tools/nthu_synth.py fetch <baseline-job-id>
python3 tools/nthu_synth.py fetch <variant-job-id>
python3 tools/nthu_synth.py compare <baseline-job-id> <variant-job-id>
```

Comparison refuses different library path/family/PVT, selected or observed tool
version, clock/reset/I/O constraints, extra constraint contents, scope/top,
compile mode, flow script, or blackbox policy/count. Use the same `scope` only for
the same hardware boundary. Source files and feature parameters can intentionally
differ between B0/X1; review their manifest hashes to ensure cache/memory sizes
and unrelated hardware choices stayed fixed. A matching string cannot prove that.
No jobs or sweeps are submitted automatically.

Area is **pre-placement standard-cell area**, in the units recorded by the
library. Timing is **pre-layout** constrained path arrival/slack, including I/O
delay for relevant paths. WNS is derived from the worst constrained max path; TNS
is left null (inspect QoR), and Fmax is left null. The tool never uses `1/period`
as measured Fmax, and has no post-layout/parasitic or frequency claim. A core and
an isolated execution unit must have different scope labels.

## Remote writes and shared-server resource policy

The developer confirmed course/department approval for the candidate library and
for detached jobs on ws25. That approval does not substitute for a working DC
license; the current smoke attempt is blocked at DC startup (see below).

All project-controlled remote payloads, outputs, logs, status, work libraries,
SVF, temporary files and caches are directed below the physical NTHU home:

```text
/home/course/u115123101/synthesis_jobs/<job-id>/
  inputs/ scripts/ logs/ reports/ outputs/ status/ work/ tmp/ cache/alib/
```

The root is configurable only as a relative path under `$HOME`. Staging verifies
its nearest existing ancestor resolves under the physical home. Launch and worker
startup independently check the physical job path and reject symlinks anywhere
in an existing job tree before writes. Jobs use `umask 077`; generated directories
are private and generated files are owner-readable/writable. The normal remote
launcher creates no files on Daisy. Uploads are explicit small RTL/header/script
packages; installed tools and the `.db` are read in place and never modified or
copied off the server.

The worker sets `TMPDIR`, `TMP`, `TEMP` to its own `tmp/` and `XDG_CACHE_HOME` to
its own `cache/`; the tcsh environment reasserts these after the site setup and
rejects a changed working directory. DC's ALIB cache and SVF output are explicit
job-relative paths. No administrator action, package install, service/cron change,
shared-install edit, broad cleanup, or manual PID killing occurs. Fetch reads the
server artifacts without moving or deleting them.

One job at a time is enforced with a per-user lock. DC is requested to use one
core, with nice priority +10 and `OMP_NUM_THREADS=1`. Children inherit limits:
no core dumps, four CPU hours and 16 GiB virtual address space per process, and
2,097,152 shell file blocks per generated file (at most 2 GiB; shell block sizes
vary). A GNU `timeout` process gives the tool a six-hour wall limit. The installed
CentOS 6 timeout lacks modern `-k`; a KILL at the deadline targets only its own
new process group. The worker remains outside that group to record failure and
release its lock. There are no automatic retries, sweeps, or workstation changes.
These are per-process limits, not aggregate cgroup or disk-quota enforcement;
review actual retained job sizes before accumulating many future runs.

On 2026-10-18 a real **shell-only storage/resource probe**, without running DC,
verified home-local temp/cache paths, directory mode 0700, file mode 0600, umask
0077, Linux ulimits, nice +10, and a timeout process group separate from its
launcher. Evidence is saved in `build/cvw/synthesis-storage-audit.json` and at
`~/synthesis_jobs/audit-20261018T071418Z/logs/audit.txt`.

This is a containment policy for our workflow, **not an OS filesystem sandbox**.
Trusted Tcl/SDC can execute arbitrary commands, and proprietary DC/site runtime
behavior has not been proven to avoid every hardcoded system temporary path.
Normal SSH/license/OS services may maintain their own system logs. The scripts
do not ask those services to write job artifacts outside home. A guarantee
covering arbitrary vendor writes would require an administrator-approved sandbox;
none is installed or enabled here.

## CV-Wally integration status and troubleshooting

The existing `tools/cvw/prepare.py` pins upstream Wally
`712ee9719467e9e9987cebd55926ae8e01b08770` and builds an unchanged RTL simulation
overlay with explicit RV64IMC/cache choices. The pinned `.deps/cvw` checkout is
now present. `tools/cvw/prepare_synth.py` reuses that preparation flow and upstream
`synthDC/scripts/wrapperGen.py`, then writes `synth/configs/cv_wally_b0.json` with
206 ordered source entries and the exact preserved B0/B1 configuration header
hash. It checks both saved simulation integration records. Run:

```sh
python3 tools/cvw/prepare_synth.py
python3 tools/nthu_synth.py submit --config synth/configs/cv_wally_b0.json --dry-run
```

The boundary is `wallypipelinedcorewrapper`, including both 16 KiB caches with
unchanged `USE_SRAM=0`, and excluding SoC/uncore RAM and simulation monitoring.
Arrays therefore map to standard cells; they are not SRAM macros or blackboxes.
The default optimization target is 10 ns with 0.1 ns uncertainty and 1 ns I/O
delays. These are declared synthesis assumptions, not a measured frequency.
`expected_wally_revision` checks the dependency HEAD; source/header hashes and
the dependency dirty flag are retained per job. See the baseline checkpoint in
`results/synthesis/baseline/` for the present startup blocker.

`docs/xqmac8.md` defines X1's architectural contract and
[`docs/cvw-xqmac8.md`](../docs/cvw-xqmac8.md) documents its implemented Wally RTL.
[Full-model simulation](../results/cvw/full-x5/README.md) now covers X1 and later
extensions. The original synthesis example templates still carry explicit
blockers and must not be treated as verified extension synthesis manifests.
There is no mapped hardware-area/physical-timing result for B0 or X1, and no
full-core synthesis job was launched.

Observed here on 2026-10-18: local unit/integration tests run without NTHU access.
Initial batch access failed at Daisy. After the developer registered their key,
explicit Ed25519 key authentication to Daisy succeeded. An authenticated nested

matches Daisy's known_hosts entry. Direct modern-client negotiation to ws25

their RSA key and authorized the scoped SSH config entries, the full doctor

One smoke job, `20261018T070704Z-71a7d2bf0c54`, was launched and its failed artifacts
fetched: DC exited 255 before running the synthesis Tcl with
`Fatal: Design Compiler is not enabled. (DCSH-1)`. No core job was launched.

resolve that startup/entitlement failure before any further synthesis attempt.

- **Authentication denied:** configure supported authorized key/agent access
  manually; do not place passwords in files. The CLI does not prompt or retry
  alternate workstations.
- **ws25 offers only `ssh-rsa,ssh-dss`:** this is host-key negotiation, before
  account authentication. OpenSSH 5.3 also predates Ed25519 user keys. With site
  permission, use an RSA user key and explicitly scope the legacy RSA/SHA-1
  exceptions to ws25 in your user-owned SSH config. Keep strict host verification;
  do not enable DSA or change global algorithm defaults. For example, merge:

  ```sshconfig
  Host daisy.ee.nthu.edu.tw nthu-ee-daisy
      IdentityFile ~/.ssh/id_ed25519_nthu
      IdentitiesOnly yes

  Host ws25 nthu-ee-ws25
      IdentityFile ~/.ssh/id_rsa
      IdentitiesOnly yes
      HostKeyAlgorithms +ssh-rsa
      PubkeyAcceptedAlgorithms +ssh-rsa
  ```

  These supplement the earlier routing snippet. Register the RSA **public** key
  on ws25, rather than the Ed25519 key, using interactive `ssh-copy-id` through
  Daisy. If selecting a dedicated RSA key instead, substitute its path in both
  the config and registration command. The agent never installs these exceptions
  automatically. Prefer a server upgrade when course administrators can provide it.
- **Forwarding denied:** a diagnostic such as `administratively prohibited` or
  `stdio forwarding failed` is distinct from authentication failure. After
  verifying Daisy-to-ws25 SSH manually, set `transport: "nested"` to stream both
  commands and transfers through a second SSH process on Daisy. It does not assume
  shared home directories. Do not copy private keys onto Daisy or enable agent
  forwarding without site authorization.
- **STAGED after scheduler acceptance:** inspect the scheduler ID with site tools;
  worker launch has not yet been observed. A disappeared/rejected queued job stays
  STAGED and requires scheduler/log inspection; it is never treated as success.
- **Version failure / missing libgraphite:** inspect `logs/version.log`; keep
  2020.09-SP5. Do not alter shared `/usr/cadtool` or install system libraries.
- **Library/license failure:** inspect `logs/dc.log`, `reports/library.rpt` and
  the fetched `failure_reason`. Confirm use permission/read access and the
  entitlement for the explicit compile mode with course staff. Do not probe the
  license server or download/copy technology databases.
- **Strict validation fails:** inspect check/design/timing, area, and log artifacts.
  Fix missing RTL/headers/models/constraints first; do not weaken validation to
  obtain an apparently successful measurement.
